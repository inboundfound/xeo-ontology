XEO — terms

Namespace https://xeoontology.org/xeo# · prefix xeo: · v0.8.0 · repo · CC BY 4.0

One standards-grounded vocabulary for how engines — search, generative, answer, conversational — see, cite, and serve content. Every term is typed by the kind of claim it makes; the strata run from durable bedrock to interpretive surface:

entityepisodeobservationderivationinterpretationnorm

A term marked extension is declared and usable but not something every implementation is expected to support. A term marked draft belongs to a module still being written and may change or be removed. A term marked deprecated is still valid; its seeAlso names what to write instead.

Modules, each needing only core: xeo-core (site, pages, queries, crawls, observations, metrics, website conversions) · xeo-visibility (AI answers, prompts, mentions, citations) · xeo-analysis (graph algorithms and what they computed) · xeo-sales (CRM records and pipeline) · xeo-attribution (touches, journeys, revenue, spend, attribution models; xeo-attribution-sales bridges it to sales) · xeo-work (clients, contracts, projects, campaigns, objectives, targets; draft: specs, work items, deliverables) · xeo-decision (gaps, diagnostics, tactics, recommendations, and the practices that govern them) · xeo-agentic (draft: agent harnesses, runtimes, sessions, model and tool calls, enforcement) · xeo-experiments (draft: arms, trials, benchmarks, claims and their checks, lessons) · xeo-knowledge (draft: company knowledge: meetings, recordings, transcripts, summaries, action items, membership) · xeo-design (draft: design systems, tokens, components, patterns, templates, assets; directions, concepts and review decisions) · xeo-align (schema.org / PROV-O / SKOS bridges). Machine-readable Turtle: core, visibility, analysis, sales, attribution, attribution-sales, work, decision, agentic (draft), experiments (draft), knowledge (draft), design (draft), align; reference values schemes (JSON); vendor mappings mappings/, one file per tool, not part of the ontology; JSON-LD context; Neo4j profile and context; SHACL shapes.

Action Item interpretation draftxeo-knowledge

xeo:ActionItem

Something a person or a team was understood to have agreed to do, read from a meeting or a message: where it was raised (raisedIn), who is to do it (assignedTo), and what, in plain language (name). An interpretation, because it is a reading of what was agreed; one a model extracted carries method and producedByModel (core). Not a WorkItem (work): an action item is what was agreed, a work item is a step someone has taken on.

Agent Runtime entity draftxeo-agentic

xeo:AgentRuntime

The product that runs the agent loop and loads a harness (Claude Code, Codex CLI, Gemini CLI, OpenCode). Identified by name with runtimeVersion: one node per version. Not a library for building agents, and not a harness: the runtime is the vendor's program, the harness is what is loaded into it.

Agent Session episode draftxeo-agentic

xeo:AgentSession

One continuous run of an AgentRuntime under one Harness, from its start to its end: immutable once ended. Identified by sessionRef. Carries startedAt, endedAt, startType, underHarness and onRuntime, and its turns (hasTurn). A resumed session keeps its sessionRef; a session begun after a clear or a handoff is a new one, which points at the old with continuesSession. High-volume: the column store keeps the rows of its calls, the graph keeps the session and what is traversed from it.

Agent Turn episode draftxeo-agentic

xeo:AgentTurn

All the work one prompt set off within a session: the model calls (hasModelCall) and tool calls (hasToolCall) between one prompt and the next. Identified by turnRef. A turn here is one prompt's worth of work; a framework that calls each pass of the model loop a turn is describing a ModelCall.

Algorithm Run episodexeo-analysis

xeo:AlgorithmRun

One execution of one algorithm over one projection of the graph at a time: immutable once finished. Carries algorithm (which method), parameters (as run), projection (what it ran on) and ranAt. The provenance record for every score and derived edge it wrote: outputs point back with computedBy, or name the run in their method. Re-running with a different projection or parameters is a new run, never an update to an old one.

Arm entity draftxeo-experiments

xeo:Arm

One version in an Experiment: the A or the B. A named condition that differs from the baseline in what it changes (testsTactic), or is the baseline itself (isBaseline). Identified by its Experiment (hasArm) and its name. Its trials are hasTrial. Its own figures on the experiment's primaryMetric, computed over those trials, are armMean, armStandardDeviation and armSampleSize.

Attributed Credit derivationxeo-attribution

xeo:AttributedCredit

One touch's credit for one conversion under one model: creditedTouchpoint, creditFor, usesAttributionModel, creditShare, and attributedRevenue and attributedConversions where they apply. The credits of one conversion under one model sum to 1 (or, for full_credit_each, each is 1).

Attribution Model normxeo-attribution

xeo:AttributionModel

A rule for giving conversions' credit to touches, described by its structure, not its name: creditRule, its CreditAnchors (positions and weights), lookbackWindow, the touch types eligible, deduplicationRule, dateBasis and revenueBasis. Vendor names such as 'U-shaped' are mapped in mappings/, not trusted: two vendors' U-shaped can put the remaining credit on different touches. A rule, so a norm; a changed rule is a new AttributionModel.

A MetricReading of an attribution Metric. The graph keeps rollups; the per-touch credits may live in the column store.

Delegation episode draftxeo-agentic

xeo:Delegation

A parent agent starting a subagent with its own context. Deliverable episode draftxeo-work

xeo:Deliverable

What was handed back for review, at a time, by a person or an agent: a change set, a document, a report. Carries occurredAt, the WorkItem it answers (fulfils) and artifactUri; where an agent made it, producedInSession (agentic) says in which session. Handing it back says nothing about whether it was accepted: that judgment is a review, which is not modelled yet. Not an Outcome, which is what was measured after the work shipped.

Design Component entity draftxeo-design

xeo:DesignComponent

A reusable piece of interface with a name and a defined anatomy: a button, a card, a header, a form field. Built from tokens (usesToken), smaller components (composedOf) and assets (usesAsset). A variant (the primary button of a button, the compact card of a card) is a component of its own that points at the one it varies (variantOf) and says what sets it apart (variantValue). Kept where it is defined, a design file or a code library (artifactUri, core); the component in the design file and the one in code are one DesignComponent where they are meant to match. Not an HTML element, and not a CMS block, though a block may implement one.

Design Concept entity draftxeo-design

xeo:DesignConcept

A rendered proposal for one piece of interface, usually under one DesignDirection: a card, a hero, a page, or a direction's version of an element of the existing site. Names what it depicts (depicts: a component, pattern, template, element or page) and the direction it was drawn under (underDirection); where it is offered in place of an element of the existing site, replacesElement names that element. Kept as an image, a design-file frame or a prototype (artifactUri, core); the tool's own id for that frame or page is its designRecordRef. Where a model drew it, method and producedByModel (core) say how. A card concept is a DesignConcept that depicts a card component. Not a skos:Concept, which is a code in a scheme.

Design Decision interpretation draftxeo-design

xeo:DesignDecision

A reviewer's call on one piece of a design proposal: keep, replace or remove an element of the existing site; approve, shortlist, send back for changes (revise) or reject a direction or a concept; or defer (designVerdict). Names what it decides on (decidesOn), who decided (decidedBy), when (occurredAt, core), and, where the call holds under one direction only, which (underDirection). A replacement may name the concept chosen (chosenConcept). The reviewer's reason in their own words is its statement (decision). An interpretation: a judgment of fit, labeled as one. A changed mind is a new decision beside the old one, never an edit of it. Not Feedback (decision), which judges a machine's claim about a gap or a recommendation.

Design Direction entity draftxeo-design

xeo:DesignDirection

One proposed visual approach for a site or a brand: a name, the idea behind it in words (statement, decision), and how it treats type, colour, imagery and layout, shown through the DesignConcepts drawn under it (underDirection). Several are usually proposed together, in one Deliverable (proposedIn, work), for one Website, Brand or Project (directionFor). A durable option that concepts and decisions point at. Whether it fits is a reviewer's call, kept as a DesignDecision about it, never as a flag on the direction. Its rank among the directions of a proposal is not a property either: a ranking is a judgment, kept as the DesignDecisions about each direction (shortlist, reject) with a statement. A design system built out of a chosen direction names it (fromDirection).

Design Element entity draftxeo-design

xeo:DesignElement

One part of an existing site's design, catalogued so it can be reviewed: a logo treatment, a colour, a type style, a style of photography, a divider, the navigation, a recurring component (elementKind). Belongs to one Website (elementOf) and is seen on its pages (seenOn). Where the same thing is also catalogued in a design system, realizedAs names the token, component, pattern, template or asset. A redesign asks of each element whether to keep, replace or remove it, and under each direction with what: a DesignDecision, and the DesignConcepts that replace it (replacesElement).

Design Pattern entity draftxeo-design

xeo:DesignPattern

A reusable answer to a recurring interface problem, made of components: a hero, a pricing table, a filtered listing, a sign-up flow. Larger than a component and smaller than a page; composedOf names the components and patterns it is made of. A pattern says how a problem is solved. Whether a page must use it is a Practice (decision), not a property of the pattern.

Design System entity draftxeo-design

xeo:DesignSystem

A named, versioned set of the decisions a brand's or a site's interfaces are built from: its tokens, components, patterns and page templates (each inDesignSystem), and the assets they use. Identified by name and designSystemVersion. Kept where it is maintained, a design file, a code library or a documentation site (artifactUri, core): the graph holds the pointer and the structure, never the files. A Website is built with one (usesDesignSystem). One built out of a proposed direction names it (fromDirection).

Design Token entity draftxeo-design

xeo:DesignToken

One named design decision stored as a value, so design files and code share it: a colour, a spacing step, a font family, a duration, a shadow. Its name (core) is its path in the token file, such as color.brand.primary; its tokenType is one of the W3C Design Tokens Format's types; its tokenValue is the value as written there. A token that refers to another (an alias, {color.blue.500} in that format) names it with aliasOf and need carry no value of its own. tokenTier says whether it is a primitive, a semantic or a component token. A token whose value changes by mode (light and dark, one brand and another; Figma calls these modes) is one token per mode, each with its tokenMode; where the value depends on more than one axis (dark and mobile), one token per combination, with one tokenMode per axis. Belongs to one DesignSystem.

Diagnostic entityxeo-decision

xeo:Diagnostic

A named, reusable check or framework that reads observations and reveals gaps (e.g. a waterfall-position assessment). The framework is durable; each finding it produces is a Gap.

Diagnostic Run episodexeo-decision

xeo:DiagnosticRun

One execution of a Diagnostic against one scope at a time: immutable once finished, method-attributed. The Diagnostic is the durable check; the run is the occasion it was applied, and each Gap it found is revealedIn that run. Carries ranAt and websiteId. A later run supersedes an earlier one without deleting it, so a finding can always be traced to the data it was read from.

Feedback interpretationxeo-decision

xeo:Feedback

An operator's judgment of a machine's claim, hung off whatever it judges (feedbackOn): a diagnosed Gap, or the Recommendation issued to close one. Carries a verdict (a slotted-in concept), a statement in the operator's words, and who gave it and when. Not a TacticAssessment, which is a scored estimate of an approach on one dimension: Feedback is a person agreeing or disagreeing with a claim about one case. Never deleted: a rejected finding and the reason it was rejected are what a Practice is later written from. A Practice promoted from a Feedback is authored (source): it stands on the operator's authority, and no experiment earned it. learned is kept for a rule earned from Experiments.

Framework normxeo-decision

xeo:Framework

A named method: a set of Stages, ordered or not, with the Diagnostics, Tactics and Practices hung on them. An optimization waterfall (ordered stages, each with a test, a subject placed at the first stage it fails), a tactic matrix, a launch checklist and a discipline playbook are all Frameworks, told apart by frameworkKind and never by subclass. A norm: it says how the work should be approached, it is authored and revisable, and it is identified by name within its author's scope. Distinct from Playbook, which is the unordered bundle a discipline reuses; a Framework adds the structure, and may include what a Playbook includes. The method is the instance you author. XEO ships the frame and none of the stages.

Harness entity draftxeo-agentic

xeo:Harness

Everything around a model that makes it act as an agent: instructions, tool guidance, memory, skills, subagent definitions, hooks, plugins, scripts, permission rules, settings. A named, versioned bundle of HarnessComponents (hasComponent), written for an AgentRuntime (runsOn). Inbound Reference observationxeo-core

xeo:InboundReference

A page on another site that links to or mentions you: your URL, Website, Brand or Organization. Observed, however it came about. Carries referencingUrl (the page), referenceTarget (what it points at or names), referenceKind (link or mention), and firstSeenAt and lastSeenAt; anchorText where it is a link. Metric normxeo-core

xeo:Metric

A named, reusable definition of a measured quantity: what is counted or computed, over which records, aggregated how, in what unit, and which way is better. A rule, not a number: the number is a MetricReading. One node per definition, identified by its skos:notation within its scheme (xeos:metric is the published reference scheme). Two Metrics are the same when metricType, aggregation, readsSlot or inputs, metricFilter, timeAnchor and unit all match; changing any of them makes a new Metric, never an edit, because readings and targets are anchored to the definition. Carries exactly one metricType, unit, betterDirection and additivity. A simple metric also carries aggregation and readsSlot; a ratio carries numerator and denominator and has unit ratio; a derived metric carries expression and at least one inputMetric. A skos:Concept, so a consumer adds its own metrics as instances without touching the ontology.

Metric Reading observationxeo-core

xeo:MetricReading

The value one Metric took over one window, for one scope, from one source. One row per metric, scope, window and source: its identity is readingOf, scope, periodStart, periodEnd, source and, where the source deduplicates in more than one way, aggregationBasis. Requires value, periodStart, periodEnd and readingOf, and may carry websiteId and datasetUri; a ratio reading also carries numeratorValue and denominatorValue. An observation only when the primary API returned exactly that metric, window and scope. When the value was rolled up, recomputed, or taken from a vendor's model, the reading is a derivation and carries method and confidence. High-cardinality readings live in the column store; the graph holds the windowed readings a target, an Outcome or an Objective points at.

The API contract of the system named in the reading's source (e.g. GSC searchAnalytics.query, GA4 runReport)

Metric Target interpretationxeo-work

xeo:MetricTarget

One measurable target of an Objective: the Metric it is set on (targetMetric, a link to the Metric node), the targetValue to reach, read per targetKind as an absolute value or as a change from a captured baseline (baselineReading), and whether it isPrimary. Unit and better direction come from its Metric. Named a target and never a key result: xeo:Outcome is 'the measured result an experiment produced', an observation, and a goal must not share a name with a reading. Each target is its own node so the experiment loop can hang observations off it; a target dropped on edit is stamped deletedAt, never destroyed, because its id is what measured history is anchored to.

termStatus xeo-core

xeo:termStatus

Whether a term is part of the core every implementation is expected to support, or of the extension set: 'core' or 'extension'. Absent means core, so every term published before this annotation existed is core without being touched. An extension term is declared, stable and usable; it is marked because only some of the systems XEO maps support the idea, and a consumer may ignore it. A third value, 'draft', marks a term of a module still being written: declared so it can be tried against data, not yet stable, and free to change or be removed without a deprecation step. A class stays draft until an example file loads it and its maintainer lifts the mark. Also carried by a concept or a scheme in the reference schemes, with the same reading. Says nothing about deprecation, which is owl:deprecated.
