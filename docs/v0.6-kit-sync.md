# XEO 0.6.0 "kit sync" — review guide

Branch `jamesmthornton/v0.6-kit-sync`, based on `a76c1e8` (0.5.0).

## What this is

`xeo-graph-kit` is gaining three courses (Graphs 101, 201, 301) and now uses XEO's names for
everything it teaches. The contract between the two repositories is the kit's
`docs/learn/GRAPH-MODEL.md`. This release makes XEO's side of that contract true:

1. it adds every term the contract marks NEW;
2. it widens or fixes the existing terms the contract uses in a way the ontology did not allow;
3. it generates a Neo4j profile from the Turtle, so the kit can check itself against XEO
   mechanically;
4. it adds SHACL shapes, worked examples and a validator, so XEO can check itself.

A second pass, on 2026-11-10, landed two research reports in the same unreleased version:
**metrics and KPIs** (what a metric is, so an Objective can target anything XEO measures) and
**CRM pipeline** (the few neutral slots that make pipeline numbers computable). They are
covered in [Metrics and CRM pipeline](#metrics-and-crm-pipeline-the-second-pass) below, which
ends with a short list of [decisions for Jim](#decisions-for-jim).

| | 0.5.0 | 0.6.0 after the kit sync | 0.6.0 now |
|---|---|---|---|
| Classes | 36 | 45 | 51 |
| Object properties | 61 | 91 | 113 |
| Datatype properties | 65 | 95 | 147 |
| Reference schemes | 20 | 29 | 50 |
| Concepts in them | 93 | 146 | 282 |
| Vendor schemes · mapped fields | 0 | 0 | 5 · 57 |
| SHACL shapes | 0 | 15 | 25 |
| Modules | 8 | 9 (`xeo-analysis.ttl`) | 10 (`xeo-metrics.ttl`), plus 5 files in `mappings/` that are not modules |

Of the 79 terms the second pass adds, 50 are core and 29 are marked
`xeo:termStatus "extension"`.

## How to review it

1. Read **Consumer impact** below first. It is the only part that touches existing terms.
2. Skim the term tables. Each new term's full definition is in its module, under the
   `# --- v0.6.0 (kit sync)` banner at the foot of the file.
3. Read the header of `xeo-analysis.ttl`. It states a position, and it is the part most worth
   disagreeing with.
4. Read **Where this differs from GRAPH-MODEL.md**. Those are changes the kit has to make.
5. Run the validator:

```bash
uv run --no-project --with rdflib --with pyshacl python tools/validate.py
```

## Consumer impact: none breaking

No term IRI was renamed or removed. No domain or range was narrowed or added. No term was
retyped, and no published code changed. All 299 subjects declared on `main` are still
declared, with their types unchanged; so are all 433 declared after the kit sync. That holds
for both passes. What the second pass does to existing terms is listed under
[What the second pass touches](#what-the-second-pass-touches), and one part of it is visible
to a consumer that filters by layer.

`launch-guardian` and `if-control-center` cite these files by line number. Every in-place
change below replaced exactly one line with one line, and every new term is appended below the
existing text, so no declaration moved. Their 33 line citations and 110 term references
resolve exactly as before (25 citations OK and the same 8 that were already wrong on `main`).

### Every domain or range that changed

All eleven are removals. Removing an `rdfs:domain` or `rdfs:range` removes an entailment and
nothing else, so no existing data changes meaning.

| Property | File:line | Removed | Reason |
|---|---|---|---|
| `embeddingRef` | `xeo-core.ttl:166` | domain `Term` | any embedded node carries it |
| `embeddingModel` | `xeo-core.ttl:172` | domain `Term` | same |
| `onEngine` | `xeo-visibility.ttl:73` | domain `LLMResponse` | a SerpSnapshot is on an engine |
| `capturedAt` | `xeo-visibility.ttl:103` | domain `LLMResponse` | **bug:** SerpSnapshot carries it |
| `model` | `xeo-visibility.ttl:107` | domain `LLMResponse` | **bug:** `inTopic` carries it |
| `occurredAt` | `xeo-engagement.ttl:77` | domain `ConversionEvent` | ExternalEvent carries it |
| `assessedAs` | `xeo-decision.ttl:120` | domain `Tactic` | production scores the Recommendation |
| `verdict` | `xeo-decision.ttl:214` | domain `Gap` | Feedback carries a verdict |
| `includes` | `xeo-strategy.ttl:80` | domain `Playbook` | a Framework includes the same things |
| `activates` | `xeo-strategy.ttl:85` | range `Playbook` | a Framework is activated the same way |
| `statement` | `xeo-strategy.ttl:108` | domain `Practice` | **bug:** Gap, Recommendation, Objective carry it |

The three marked **bug** were asserting something false. `rdfs:domain` is an entailment rule:
with `capturedAt` domain-locked to `LLMResponse`, every `SerpSnapshot` that carried a capture
time was inferred to be an LLM response.

`occurredAt`, `verdict` and `statement` are not in the brief. They are the same defect, and
the new terms would have triggered it (an `ExternalEvent` typed as a `ConversionEvent`, a
`Feedback` typed as a `Gap`).

Where the old domain is still the usual case, it is kept as a hint
(`xeo:domainIncludes`), which entails nothing.

### Descriptions edited in place

One line each, same line number: `Topic`, `linksTo`, `hasResult`, `embeddingRef`, `name`,
`resultType` (core); `onEngine`, `model` (visibility); `assessedAs`, `verdict` (decision);
`includes`, `activates` (strategy). Each edit adds the new case and removes nothing. The
hosting comment at `xeo-core.ttl:8` and the eight `owl:versionInfo` lines also changed in
place.

### Triples added to existing terms

Appended at the foot of each module, as extra statements about a term declared above:

- an `rdfs:label` for all 126 existing properties (none had one);
- a `dct:description` for the 23 terms that lacked one, and an `xeo:epistemicLayer` for the 9
  that lacked one (the `Engine` and `ConversionPoint` subclasses, `origin`, `address`);
- `appliesToConcept rdfs:subPropertyOf appliesTo`, and
  `appliedPractice rdfs:subPropertyOf evaluatedPractice`;
- `domainIncludes` / `rangeIncludes` hints on `evidencedBy`, `assessedAs`, `verdict`,
  `includes`, `activates`, `statement`, `inScope`.

### What the second pass touches

Nothing a consumer stores or cites changes. Four kinds of change reach existing terms.

**1. Three layer annotations were corrected.** This is the only change a consumer could
observe: a query that selects terms by `xeo:epistemicLayer` (or a graph stamped from the
profile's `layer`) will find these three one layer over.

| Term | File:line | Was | Now | Why |
|---|---|---|---|---|
| `measures` | `xeo-delivery.ttl:123` | observation | episode | it records an experiment's design, fixed at setup; nothing is measured by it |
| `mentionRate` | `xeo-visibility.ttl:123` | observation | derivation | a share computed over a sample, from mentions a method extracted |
| `citationRate` | `xeo-visibility.ttl:128` | observation | derivation | same |

`etv` is the fourth layer fix and touches no existing triple: the concept never carried a
layer. Its Metric (`xeos:metric-etv`) now says every reading of it is a derivation, and the old
concept gained an editorial note.

**2. Nine advisory deprecations.** `owl:deprecated true` plus an `rdfs:seeAlso` to the
replacement, appended at the foot. Each term stays declared, typed and valid; no validator,
shape or generator rejects it; existing data is unaffected. The flag tells a new
implementation which form to write.

| Deprecated | Write instead | Why |
|---|---|---|
| `lift` | `absoluteChange` and `relativeChange` | one number that could be points or a percentage |
| `direction` | `betterDirection` on the Metric | its own description said it is derived from the metric |
| `CallToAction`, `LeadCaptureForm`, `GatedAsset` | `conversionPointType` (`cta`, `lead_form`, `gated_asset`) | values modelled as classes; the list was growing |
| `Informational`, `Navigational`, `CommercialInvestigation`, `Transactional` | the `xeos:searchIntent` concepts | values modelled as individuals |

Not deprecated, though the reports proposed changing them: `metric` (kept a string),
`magnitudeUnit` (`magnitudeMetric` sits beside it), `baseline` (kept as the cached value of
`baselineReading`), `xeos:objectiveMetric` (kept, see below), `targetKind`'s `percent`,
`SearchIntent` (still the range of `targetsIntent`), `crmRecordRef`.

**3. Descriptions tightened in place**, one line for one line, same line number:
`Objective`, `MetricTarget`, `resultsWindowDays`, `metric`, `direction`, `targetKind`,
`targetValue`, `baseline` (delivery); `Outcome`, `lift`, `magnitudeUnit` (decision);
`SearchIntent`, `ConversionPoint`, `ConversionEvent`, `crmRecordRef`, `attributedResponse`,
`occurredAt` (engagement); `periodStart`, `periodEnd` (core); and in the schemes the
descriptions of `objectiveMetric` and `targetKind` and the definition of
`below_volume_floor`. Each adds a rule or a pointer; none withdraws anything a term allowed.
`crmRecordRef` is the one to read: it now says the value is written
`crmSystem:crmTenantId:crmObjectType:recordId` and that a form id does not belong in it. The
range is still `xsd:string`, and a bare id stored earlier is still valid.

**4. Triples added to existing terms**, at the foot: `groundedIn` on `capturedBy` and
`hasConversionPoint`; `skos:altLabel "KPI"` on `isPrimary`; `rdfs:seeAlso` from `baseline`,
`magnitudeUnit` and `crmRecordRef` to their new companions; `skos:exactMatch` from each of the
eight `objectiveMetric` concepts to its Metric, and an editorial note on `ctr` and `etv`.

**One shape was relaxed.** `MetricTargetShape` required `direction`. A shape cannot require a
deprecated property, so `direction` is now optional and still checked when present (one value,
`up` or `down`). Data that passed before still passes.

**`schemes.json` grew, compatibly.** `schemes` keeps its shape. A concept gains keys
(`matches`, `altLabels`, `status`, `editorialNote`, `metric`) only where the Turtle states
them. The vendor crosswalks are under a new top-level key, `vendorSchemes`.

The shapes are conservative. Each checks one rule a term's description already makes, and none
closes a class. What they check: `confidence`, `similarity`, `mentionRate` and `citationRate`
are between 0 and 1; a `magnitude` has a `magnitudeUnit` and the reverse; a `URL` has one
`address`; a `Domain` has one `name`; a `SerpSnapshot` has `capturedAt`; an `LLMResponse` has
`capturedAt` and `model`; a `MetricTarget` has one `metric` and a `direction` of `up` or
`down` (since the second pass the `direction` is optional, and checked when present); an
`Outcome` has one `result`; a `Practice` has a `statement`, one `practiceKind` and
one `status`; a `Stage`'s `stageOrder`, when present, is one integer; an `AlgorithmRun` has
one `algorithm` and a `projection`.

The ten added by the second pass: a `Metric` has exactly one `metricType`, `unit`,
`betterDirection` and `additivity`; a simple Metric has an `aggregation` and a `readsSlot`; a
ratio Metric has a `numerator`, a `denominator` and unit ratio; a derived Metric has an
`expression` and an `inputMetric`; a `MetricReading` has one `readingOf`, `value`,
`periodStart` and `periodEnd`; a reading of a currency Metric has a `currencyCode`; a target on
`pipeline_created` or `revenue_won` has a `targetCurrency`; a `dealAmount` has a
`currencyCode` and is not negative; a currency code is three upper-case letters; a
`StageTransition` has a `crmRecordRef`, a `toStageRef` and an `enteredAt`. The typed Metric
rules fire only for the published `xeos:metricType` concepts. The currency-target rule lists
the two deal-amount metrics and leaves `etv` alone, because `etv` was targetable before
`targetCurrency` existed. The validator also holds all 35 published Metrics to these shapes.

## Where this differs from GRAPH-MODEL.md

Places where the contract asked for something XEO's conventions do not allow, or left
something out. The convention-respecting thing was done. Each needs a matching change, or a
decision, on the kit side.

1. **Fetch observations belong on the `FETCHED` edge, not the `URL` node.** The contract puts
   `title`, `statusCode`, `indexable`, `wordCount`, `crawlDepth`, `h1` and `contentType` on
   `(:URL)`. XEO's rule, which lesson 101 itself teaches, is that the address lasts and the
   rest is what one crawl saw. The new slots say "carried on fetched". A copy on the node is
   allowed as a cache of the latest crawl and should say which crawl it came from.
2. **Five of the crawl slots are derivations, not observations**: `indexable`, `wordCount`,
   `crawlDepth`, `contentHash`, `linkPosition`. Each is a crawler's computation with no
   primary standard behind it. The kit's `xeoLayer` stamp for them should be `derivation`.
3. **`xeoLayer` is not an XEO term.** The contract says every node and relationship carries
   `xeoLayer` (called `layer` until 2026-11-10, renamed so it reads as XEO's layer and nothing else's). XEO types terms with `xeo:epistemicLayer` and has explicitly not decided to own an
   instance-level property (`xeos:epistemicLayer` says so). The profile records `xeoLayer` as a
   convention (`conventions.layerKey`) and gives the value for each label and type. No
   `xeo:layer` was minted.
4. **Property keys the contract uses that XEO does not declare, and that are not marked NEW**:
   `path` (URL), `code` (Diagnostic), `level` (on `REQUIRES_CAPABILITY`), `hypothesis`
   (Experiment), and the surrogate `id`. None was added: they were not asked for, and `level`
   has no stated meaning to define. The kit's alignment check will report them. Either put
   them on the kit-local list or propose them for 0.7.
5. **Concept slots come in two forms.** `algorithm`, `basis`, `frameworkKind` and
   `organizationKind` are object properties to a `skos:Concept`, the idiom of `gapType` and
   `execution`. The contract stores each as a code on the node or edge. Both are conformant,
   and the profile lists each slot as a relationship type and as a property key
   (`"conceptSlot": true`).
6. **`sentiment`, `linkPosition` and `device` are controlled strings, not concept ranges.**
   The brief called `sentiment` a concept slot. Core and visibility stand alone on primary web
   standards and take no SKOS dependency, so they follow `resultType`: a string code with a
   published scheme. For the kit this changes nothing.
7. **`Gap {magnitude}` needs `magnitudeUnit`.** The contract's Gap carries a magnitude and no
   unit. XEO's rule (now a shape) is that a magnitude never travels alone.
8. **`Feedback {verdict}` reuses `xeo:verdict`** with its domain opened, and its values are
   the `feedbackVerdict` scheme. `Gap {statement}` and `Recommendation {statement}` reuse
   `xeo:statement` the same way.
9. **`suggests` is a norm, `atStage` is a norm.** The contract does not give layers for them.
   A diagnostic's usual response is a standing claim about a class of cases.
10. **`communityId` is an integer**, and `parameters` is one serialized JSON string.
11. **`Entity` is a hazardous name.** It collides in conversation with the epistemic layer
    `entity`. It was added as asked, and its description says which sense it means.

## Metrics and CRM pipeline: the second pass

Two research reports arrived on 2026-11-10, each answering a brief: **metrics and KPIs**
(eleven vendors and standards read) and **CRM pipeline** (seven CRMs read). Neither ran an API
call, so nothing in them is verified against live output. Their recommendations are landed
here under one constraint: **no breaking change**. Where a report asked to rename, retype,
split, move or remove an existing term, the new form was added beside the old one, and the old
one was deprecated only as advice.

### How core, extension and deprecated are marked

- **`xeo:termStatus`**, an annotation property declared once in `xeo-core.ttl`. Its value is
  `"extension"` on a term (or a reference scheme, or a concept) that is declared and usable but
  that only some of the surveyed systems support. A term with no status is core, so nothing
  published earlier had to be touched. 29 terms and 7 schemes carry it.
- **`owl:deprecated true`** with **`rdfs:seeAlso`** naming the replacement. Advisory.
- **`xeo:mappingConfidence`**, an annotation property declared in `xeo-core.ttl` and used only in `mappings/`:
  `"documented"`, `"inferred"` or `"verified"`. No mapping is verified yet.

All three are carried into `neo4j-profile.json` (`status`, `deprecated`, `replacedBy`),
`schemes.json` and the term docs, and the validator checks them.

### The metrics and KPIs report: adopted, and adopted differently

**Adopted as proposed:** the `Metric` class at the norm layer with all its computation
properties; `MetricReading`; the split of definition from value; no KPI class (`isPrimary`
gained the alt label "KPI"); ratios as 0 to 1 quotients rolled up from their parts;
`minDenominator` bound to `below_volume_floor`; `baselineReading` and `resultReading`;
`absoluteChange` and `relativeChange`; `resultsWindowStart`; the whole extension set; the
impact-reporting rules, written into the descriptions of `Outcome`, `absoluteChange` and
`objectiveReading` (an Objective is one reading over its deduplicated scope, never a sum of
Outcomes).

**Adopted differently:**

| The report asked for | What was done | Why |
|---|---|---|
| Retype `metric` to an object property | It stays a string. Its description now says the string is the notation of a Metric in `xeos:metric` | consumers store the code |
| Rename `xeos:objectiveMetric` to `xeos:metric` | `xeos:metric` built beside it; the old scheme and its eight concepts kept, each an `exactMatch` of its Metric | consumers reference the old IRIs |
| Name the AI rates `ai_mention_rate` and `ai_owned_source_rate` | The Metrics keep the published codes `mention_rate` and `citation_rate`; the report's names are alt labels | a stored code must resolve |
| Change `ctr`'s unit from percent to ratio | Done. The Metric `ctr` has unit ratio, and the old concept's note was corrected to ratio (decided 2026-11-11), with an editorial note | stored values were not checked first; see Decisions |
| Deprecate `direction`, `lift` | Deprecated as advice; both stay valid | no breaking change |
| Split `magnitudeUnit` into `magnitudeMetric` | `magnitudeMetric` added beside it; `magnitudeUnit` stays required with `magnitude` | a size such as words is not a value of any Metric |
| `targetKind` values absolute, relative, absolute_change | `relative` and `absolute_change` added; `percent` kept | a published code is never renamed |
| `periodStart` / `periodEnd` as `xsd:dateTime`, end exclusive | The existing core terms are reused: `xsd:date`, end inclusive | they cannot be retyped; see Decisions |
| A new `sourceSystem` property | Not minted. A reading uses `xeo:source`, which already means this on a rollup | one property for one thing |
| `readsSlot` always names an XEO slot | Where XEO has no slot under the number (sessions, key events, a vendor's modelled value), `readsSlot` is `xeo:value` | there is no analytics module to point into |
| Ratios without declared parts | Eight component Metrics added so every ratio has a numerator and a denominator that are Metrics | the ratio shape requires them |
| `closeMatch` from `Metric` to the OSI metric | Not added | the report gives no IRI for it |

Two smaller widenings of the report's definitions, both stated in the descriptions:
`expression` may also state a row-level computation on a simple metric (`sales_cycle_days`),
and `minDenominator` applies to a mean (the number of values averaged) as well as a ratio.
The report lists `websiteId` and `datasetUri` as required on a reading, and
`numeratorValue` / `denominatorValue` as required on a ratio reading; the descriptions say
so, and the shape enforces only `readingOf`, `value` and the window, because a
vendor-returned rate often comes without its parts.

### Where the reports disagree, with each other or with the ontology

Not resolved here; each is either a Decision below or needs live data.

1. **Window end.** The metrics report wants `periodEnd` exclusive and a `dateTime`. Core's
   `periodEnd` is an inclusive `date`, and readings reuse it.
2. **Pipeline reading layer.** Observation (metrics report) or derivation (CRM report). The
   second was followed.
3. **Where a rollup lives.** `MetricReading` is canonical in the column store;
   `PipelineRollup`, its subclass, is canonical in the graph, as the CRM report has it.
4. **Does GA4 have an AI-assistant channel?** The CRM report says yes, from 13 May 2026, on
   secondary sources. The metrics report found no native GA4 equivalent. No GA4 field is mapped
   to `ai_assistant_sessions`.
5. **Profound's visibility denominator.** Profound's help center and glossary disagree. Only
   live output settles it.
6. **`ctr` unit.** Both reports and every source say ratio; the published concept said percent,
   and now says ratio.
7. **Lifecycle stage.** Jim's notes put it in the common core; the CRM report finds one CRM of
   seven carries it natively.
8. **"Original source".** Jim's notes treat it as an observation; the CRM report shows it is a
   classifier's output or a manual picklist. It is a derivation here. Decided 2026-11-11: it
   stays a derivation. The test: if two tools could read the same raw facts and give different
   answers, the value is a derivation and carries the method that produced it.

### Decisions for Jim

1. **`ctr` unit. Decided 2026-11-11: corrected to ratio now.** `xeos:objectiveMetric-ctr` said
   "unit percent". The sources return a quotient, and `xeos:metric-ctr` says ratio. The note was
   corrected without first checking stored values, so this is still owed: check whether stored
   `ctr` targets and baselines in launch-guardian and if-control-center hold 5 or 0.05.
   The same question applies to `targetKind` `percent` (20 or 0.2), which is why `relative` is
   a `closeMatch` to it and not an exact one.
2. **Flip `metric` to an object property at 1.0?** It is a string holding a Metric's code.
   The report's design is `MetricTarget → Metric`. A breaking change, so a 1.0 question.
3. **Lifecycle stage is an extension, not core.** The report disagrees with your notes, on
   evidence (one CRM of seven). Confirm, or say that HubSpot-first is reason enough to promote
   it.
4. **Should the nine advisory deprecations become removals, and when?** The changelog's rule
   since 0.3 is that a term is never removed. Either they stay deprecated indefinitely or 1.0
   is where the rule is relaxed, once.
5. **Verify the vendor mappings against live API output before any classifier is trained on
   them.** First: `GET /crm/properties/2026-09/deals` and `/contacts` on the client portal, for
   the three HubSpot names marked inferred and the ones left out. Then one Profound response,
   to settle the visibility denominator.
6. **Three layer annotations moved** (`measures`, `mentionRate`, `citationRate`). Confirm no
   consumer filters on the old values.
7. **Window convention.** Keep the inclusive `date` window core already publishes, or move to
   the report's exclusive `dateTime` end with new properties at 1.0.
8. **`mention_rate` or `ai_mention_rate`.** The published codes were kept and the report's
   names made alt labels. The AI metrics added now do carry the `ai_` prefix
   (`ai_share_of_voice`), so the set is not uniform. Say if you want aliases minted.
9. **What is a CRM pointer node? Decided 2026-11-11: both labels.** `CrmRecord` is minted, a
   pointer whose only identity is `crmRecordRef`, and the record-level pipeline properties hint
   at it with `domainIncludes`. An implementation may add the vendor's own label beside it on
   the same node (`:CrmRecord:HUBSPOT_Contact`); that label is the implementation's convention,
   never an XEO term. Which CRM is `crmSystem`, and which kind of record is `crmObjectType`.
10. **The inferred defaults.** The `minDenominator` values, the nine `acquisitionChannel`
    values other than `ai_assistant`, and the `valuePeriod` codes are stated defaults, not
    vendor facts. Adjust or accept.
11. **Is an AI overview on a results page `ai_assistant`? Decided 2026-11-11: neither.** It is
    its own value, `ai_overview` (extension). The visit comes from a results page, so it is not
    an assistant's; a generated answer sent it, so it is not an ordinary result. No source read
    reports it separately (HubSpot counts only AI-specific domains; GA4's list is unpublished),
    so nothing fills it yet. Being cited in an overview already counts toward citation rate.
